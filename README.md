# КодФормула

Образовательная веб-платформа для подготовки школьников 1–9 классов по спортивному программированию.

Проект выполнен для кейса «Образовательная платформа для подготовки по спортивному программированию» чемпионата Чувашской Республики по спортивному программированию.

## 1. Назначение

«КодФормула» разделяет учебный процесс на три рабочих контура:

- **Ученик** — проходит курс, выполняет задания, отправляет решения, получает результат и видит прогресс.
- **Куратор** — сопровождает учеников, отвечает на вопросы и проверяет работы, которые нельзя или нецелесообразно проверять автоматически.
- **Администратор** — создаёт и публикует курсы, собирает курс из разнотипных шагов, назначает учеников и кураторов.

Основная продуктовая идея: курс не является набором однотипных страниц. Он состоит из **шагов разных типов**, у которых могут отличаться форма ответа и способ проверки.

## 2. Что реализовано

### Роли

| Роль | Реализовано |
|---|---|
| Ученик | каталог курсов, прохождение шагов, ответы, отправка кода/работы, статусы, прогресс, история, обратная связь |
| Куратор | очередь работ, ручная проверка, возврат с комментарием, ученики, аналитика |
| Администратор | курсы, конструктор шагов, пользователи, назначения, публикация, аналитика |

### Типы учебных шагов

В базе предусмотрены:

- `theory` — теория;
- `question` — контрольный вопрос;
- `tests` — задача с прогоном по тестам;
- `scratch` — ручная проверка проекта Scratch;
- `minecraft` — ручная проверка задания Minecraft Education;
- `project` — проектный шаг.

Способ проверки хранится отдельно от типа шага: `read`, `auto` или `manual`.

### Автоматическая проверка

Для автоматических шагов реализованы:

- проверка ответа;
- проверка набора ответов;
- выполнение Python-решения;
- сравнение фактического вывода с ожидаемым;
- статусы `accepted` / `failed`;
- отображение результата ученику;
- обновление прогресса.

Для Python-проверки процесс запускается с системным `timeout` на 2 секунды на тест.

> **Важно:** текущий код запускает Python в отдельном процессе ОС, но не предоставляет полноценную контейнерную sandbox-изоляцию и лимит памяти. Перед production-развёртыванием online judge необходимо вынести выполнение пользовательского кода в отдельный изолированный worker/container с CPU/RAM/time limits.

### Ручная проверка

Для файловых/проектных работ:

1. ученик отправляет работу;
2. создаётся запись `submissions` со статусом `review`;
3. работа попадает в очередь куратора;
4. куратор принимает или возвращает работу;
5. при возврате комментарий сохраняется;
6. ученик видит статус и обратную связь;
7. при принятии прогресс шага становится `done`.

Поддерживаемые MIME-типы загрузки:

- PNG;
- JPEG;
- PDF;
- TXT;
- ZIP.

Максимальный размер файла — 8 МБ.

## 3. Учебная модель

Структура:

```text
Курс
└── Модуль
    └── Шаг
        ├── тип
        ├── содержимое
        ├── форма ответа
        ├── правило проверки
        └── данные, необходимые проверяющему
```

В БД тип шага отделён от конкретного шага:

```text
step_types
    ↓
steps
    ├── content_json
    ├── validation_json
    └── teacher_only_json
```

Это позволяет добавлять новые типы без изменения таблиц курсов, модулей и прогресса.

### Разграничение доступа

Сервер проверяет роль через `require_auth()` / `require_any_role()`.

Примеры:

- `course-admin.php` — только `admin`;
- `step-admin.php` — только `admin`;
- `review.php` — `curator` или `admin`;
- `progress.php` — `student`;
- `upload.php` — `student`.

Это важнее скрытия ссылок в интерфейсе: API также проверяет роль.

## 9. Установка

### Вариант A — XAMPP

1. Установить XAMPP с Apache, PHP и MySQL.
2. Скопировать папку `kodformula` в:

```text
C:\xampp\htdocs\kodformula
```

3. Запустить Apache и MySQL.
4. Открыть phpMyAdmin.
5. Создать БД:

```text
kodformula
```

с кодировкой `utf8mb4`.

6. Импортировать:

```text
database/schema.sql
```

7. Проверить настройки в:

```text
config/config.php
```

8. Открыть:

```text
http://localhost/kodformula/
```

### Вариант B — встроенный PHP-сервер

Из директории проекта:

```bash
php -S localhost:8000
```

Но MySQL всё равно должен быть запущен, а `config/config.php` должен содержать корректные параметры подключения.

Рекомендуемая последовательность:

6. Опубликовать курс.
7. Показать назначение ученика и куратора.

### Сценарий 2 — ученик

1. Войти как `masha`.
2. Открыть назначенный курс.
3. Показать прогресс.
4. Открыть теоретический шаг.
5. Выполнить контрольный вопрос.
6. Показать изменение статуса/прогресса.

### Сценарий 3 — автоматическая проверка

1. Открыть задачу с тестами.

3. Показать `accepted`.

5. Вернуться под `masha`.

- [ ] Apache/PHP/MySQL запускаются с нуля.
- [ ] `schema.sql` импортируется в чистую БД.
- [ ] Работают 3 роли.
- [ ] Работает создание курса.
- [ ] Работает добавление разнотипных шагов.
- [ ] Работает публикация.
- [ ] Работает назначение ученика/куратора.
- [ ] Ученик видит курс.
- [ ] Прогресс меняется.
- [ ] Автопроверка возвращает результат.
- [ ] Ручная работа попадает в очередь.
- [ ] Куратор может принять/вернуть работу.
- [ ] Комментарий виден ученику.
- [ ] История отправок сохраняется.
- [ ] Чужие административные API не открываются обычному ученику.

### Отдельно проверить перед показом

1. Бесконечный цикл в Python не зависает.

4. Недопустимый MIME отклоняется.
5. После logout сессия действительно завершается.
6. Сценарий можно пройти без изменения БД вручную.

## 15. Известные ограничения текущего MVP

Эти пункты не следует выдавать за уже реализованные возможности.

### 15.1. Изоляция запуска пользовательского кода

Сейчас Python запускается отдельным процессом с `timeout`, но полноценного sandbox/container isolation и ограничения памяти нет.

Для production:

```text
API
 ↓
Queue
 ↓
Isolated worker/container
 ↓
CPU / RAM / time limits
 ↓
Verdict
```

### 15.2. Рейтинг

В БД есть `score_events`, однако полноценная формула рейтинга и отдельный рейтинг/лидерборд в текущем UI не завершены.

Для полного соответствия критерию рейтинга необходимо:

- определить формулу;
- записывать score events при автоматической и ручной проверке;
- показывать разбивку результата ученику;
- отделить рейтинг от процента прохождения курса.

### 15.3. Версионирование опубликованных курсов

У курса есть поле `version`, но полноценные снимки версии шага/курса пока не реализованы.

Для требования «изменение опубликованного курса без потери исторических результатов» production-версия должна хранить версию контента, к которой относилась каждая отправка.

### 15.4. CSRF

PHP-сессия и серверные проверки ролей реализованы. В сессии также создаётся CSRF-токен, но полноценная проверка токена на всех изменяющих API-операциях требует дополнительного middleware.

## 16. Безопасность

Уже реализовано:

- серверная проверка авторизации;
- серверная проверка ролей;
- `password_hash()` / `password_verify()`;
- prepared statements через PDO;
- `session_regenerate_id(true)` после входа;
- MIME-проверка загружаемых файлов;
- ограничение размера файла;
- случайные имена загруженных файлов.

Для production необходимо дополнительно:

- HTTPS;
- CSRF middleware;
- секреты через environment;
- защищённая раздача загруженных файлов;
- rate limiting;
- изолированный code runner;
- лимит CPU/RAM;
- аудит административных действий;
- полноценное версионирование опубликованных курсов.

## 18. Быстрая архитектурная формулировка для защиты

> «Мы разделили платформу на три роли и вынесли курс в расширяемую модель шагов. Шаг хранит контент, тип ответа и правила проверки. Поэтому теория, тест, программная задача и проектная работа могут жить в одном курсе, но проходить разные проверки.
